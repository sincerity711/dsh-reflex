# Teams 会议结束确认

日期：2026-10-29。用户已确认交互方案；本文供实现前审阅。

## 问题与目标

当前主程序在 `src/core.ts` 将 Teams 的 `leaveGraceSec` 默认覆盖为 0。一次扫描找不到会议窗口即产生 `ended(left)`。2026-10-28 本机日志显示同名会议在数秒内结束并重新开始。这里的 `left` 是推断，不是用户挂断的证据。

目标：窗口暂时不可读时继续原会议，提示用户恢复 Teams 窗口或确认结束；120 秒内恢复则继续同一记录，无操作且持续无法确认满 120 秒才结束。

## 已选择的方案

采用“120 秒等待 + 用户确认”。仅恢复延迟无法解释当前状态或让用户提前结束；完全手动结束又会留下无人处理的采集。因此保留自动超时，但明确它只是检测超时。

现有 SwiftUI 状态栏面板是主要入口，保持其布局、字体和中英文支持。不新增独立设置页面，不改动 Teams 窗口，不执行挂断。

## 状态与行为

| 当前状态 / 输入 | 结果 |
| --- | --- |
| 空闲，识别到会议 | 沿用开始事件和字幕采集流程 |
| 会中，无法识别会议、Teams 不可见或疑似标题变化 | 进入等待确认，保留会议 ID、原标题和采集任务；启动 120 秒期限 |
| 等待中，恢复识别原会议 | 回到会中，取消期限；不产生新开始事件 |
| 等待中，持续未恢复 | 保持原始期限，不因每次扫描重置 |
| 等待中，用户点“仍在开会” | 从操作时刻重新给予 120 秒；保留原会议并提示恢复窗口 |
| 会中或等待中，用户点“会议已结束” | 发出一次结束事件，reason 为 `user_confirmed`；正常收尾并进入原纪要流程 |
| 等待期限到达，尚未恢复或续期 | 发出一次结束事件，reason 为 `detection_timeout`；正常收尾并进入原纪要流程 |

结束事件的 `endedAt` 使用确认或超时发生时刻；另记首次丢失观测时间，避免把推测的离开时刻写成确定事实。

原来的 `replaced` 立即结束路径也必须进入等待。悬浮窗前缀、后缀等界面文字不得单独造成会议身份改变。能从窗口关联和已知会议标题确定是原会议的，继续原会议；无法确定时进入等待，保留观察到的候选标题供诊断。

扫描抛错不能无限跳过状态机：将无法完成观测视为不确定状态，走同一等待流程，同时保留错误原因。辅助功能无权限、程序不可用与用户离会不能使用同一个原因描述。

手动结束后，仍然存在的同一会议窗口不能在下一次扫描立即启动新记录。保存被用户结束的会议身份，直到观察到离开后重新加入，或识别到明确不同的会议；支持程序重启后保留该抑制状态。不以一次短暂缺失作为重新开始的充分依据，使用连续 120 秒无原会议证据作为清除条件。明确不同的会议可正常启动。

## 用户界面

- 等待时显示“等待确认”，保留原会议标题和已有字幕。
- 显示：“暂时无法检测会议。请恢复 Teams 会议窗口；如果会议已结束，请确认。”附剩余秒数，并说明倒计时结束会自动结束记录。
- 提供“仍在开会”和“会议已结束”。正常采集中也保留手动结束入口。
- 每次进入新的等待阶段提示一次，不随每次扫描重复弹出；续期不重复发起提醒。恢复后再丢失属于新阶段。
- 提醒沿用现有本机通知能力，面板内提示不依赖通知权限；不要自动抢焦点。
- 点击时显示处理中；失败保留可重试操作和错误说明，不假装已结束。
- 明确“会议已结束”只结束 Reflex 记录并生成纪要，不挂断 Teams。

## 实现边界与数据流

1. `MeetingTracker` 作为会议生命周期唯一权威，处理观测、确认、续期、截止时间和结束抑制状态，持久化到现有 checkpoint。
2. `TeamsScanner` 提供窗口分类、控件命中、标题和不可读原因。状态机不从 UI 文案反推状态。
3. `Program.watch` 将等待状态、correlationId、首次丢失时间、deadline 和原因发布到 program status；冻结字幕仍使用原 5 秒逻辑，不触发会议结束。
4. 移除主程序注入的零秒宽限。配置缺失、零值或负值不能重新启用立即结束；统一回退到 120 秒，保留有效正数覆盖的兼容性。
5. 状态栏按钮通过 helper 向 Teams 程序传递明确命令，携带 correlationId 与请求 ID；复用现有认证与进程消息通道，补充最小命令消息及响应。不要用修改配置或伪造会议事件传递命令。
6. 命令与扫描在同一个状态更新序列中处理。拒绝过期会议 ID，重复请求幂等；截止时间与确认竞争时最多产生一次结束事件。响应应反映程序应用命令后的状态。
7. 真正结束统一发出 `teams.meeting.ended`，继续现有 stopOn → 字幕收尾 → summarize 流程；不直接取消 capture 任务。

## 日志

记录状态转换、触发源（扫描/用户/超时）、原状态和新状态、会议 correlationId、deadline、窗口分类、锚点是否命中以及扫描错误。标题沿用项目的脱敏策略，记录长度与摘要；不增加字幕正文或窗口全文转储。

现有事件日志保留最终 reason。新增诊断要能回答“为什么进入等待”“为什么最终结束”“是不是用户操作”，避免继续将检测失败记作已确认离会。

## 验收与验证

- 窗口丢失 1 秒、5 秒、119 秒均不结束采集；120 秒持续丢失仅结束一次。
- 期限前恢复同一会议，不产生新 ID、新任务或纪要。
- 续期从操作时刻开始计时；恢复后再次丢失建立新期限。
- 用户确认立即正常收尾；下一次仍看到原窗口不会自动重开。
- 标题切为 compact view、切 Space、最小化、扫描抛错均不直接结束。
- 过期按钮、重复请求、确认与超时竞争不会结束新会议或重复生成纪要。
- checkpoint 恢复保留等待期限与手动结束抑制；旧 checkpoint 可兼容读取。
- 零值配置不能恢复立即结束；程序 status 的等待状态进入菜单快照。
- 状态机使用可控时间测试；消息协议和 helper 路由验证成功、失败、重复和过期操作；菜单验证倒计时、按钮和中英文状态。
- 执行仓库相关 TypeScript 和 Swift 检查。最后手动复现前后台切换，检查提示、记录连续性和日志。
